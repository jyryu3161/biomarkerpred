# BioMarkerPred maintenance instructions

- Maintain the v0.4.2 analysis design and interface. v0.4.3 contains confirmed bug fixes; nested cross-validation, external validation, report expansion, automatic post-download checks and timeout changes are outside this maintenance scope.
- Delegate each implementation stage to one subagent, then have the primary session review the changes and run relevant checks before advancing. Do not edit the same files concurrently. Preserve existing user work.
- Use synthetic fixtures for development, CI and Docker verification. Never upload patient data. Do not change evaluation design silently or use prediction batches to fit model parameters or thresholds.
- Keep CLI and GUI behavior, saved model/results metadata and displayed status consistent. Preserve unavailable metrics and their reasons. Inspect outputs as well as process exit status; a failed analysis must not be shown as successful.
- Read README.md, the requested configuration and input headers before an analysis. Confirm outcome coding and time units from explicit configuration; do not infer them from filenames. `time_variable` names the survival-time column; `horizon` is numeric in those same units.
- Preserve the exact v0.4.2 Docker runtime pinned in Dockerfile. Do not refresh package installations or dependency locks to work around a failure. The application version is separate from the saved-model format version.
- Run `./scripts/sync-version.sh v0.4.3` and `node scripts/check_release_version.cjs v0.4.3` for release metadata. All Docker entrypoints must use the matching versioned image.
- For survival changes, run `Rscript tests/test_survival_bugfixes.R` from the repository root, preferably inside the pinned Docker runtime. The script reports when optional real-estimator/plot checks are skipped. Verify that a patient's score and risk group are unchanged between single and batch prediction.
- For desktop changes, use `cd gui && npm ci && npm test && npm run build` and `cd gui/src-tauri && cargo test --locked`. Run targeted formatting/lint checks and report pre-existing failures honestly. Do not rerun unrelated expensive checks after a documentation-only change.
- Distinguish controlled Docker/IPC tests, Linux container execution, and actual installed desktop behavior. Passing builds or unit tests do not establish Windows Docker Desktop or other operating-system compatibility.
- Routine local implementation does not authorize publication. Preserve the user's explicit release/removal authorization; the primary session performs authorized remote mutations after review. Never move an existing published version to different artifacts.
